## Delivered support workflow

Requesters (authenticated active customers, owners, staff or admins using personal
routes) can create and list their own requests, read paginated conversations and
reply while the request is open. Owners cannot read a customer's request merely
because the customer visited their gym. Personal endpoints remain owner-scoped
even for an administrator; the separate admin API supplies explicitly privileged
queue/detail/reply/status operations for ADMIN/SUPER_ADMIN.

Categories: ACCOUNT, BOOKING, GYM, TECHNICAL, OTHER. These are support topics,
not authority to perform financial actions or retrieve account data.
Statuses: OPEN, WAITING_USER, RESOLVED. Only admins change status or reopen a
resolved thread. Replies do not infer status automatically. No deletion or editing
of message history is exposed. ORM updates/deletes of messages are rejected;
database administrators can still modify records through SQL, so this is not
immutable external evidence or a retention/deletion policy.

Creation and replies require Idempotency-Key. Keys are scoped to requester or
ticket/author; retrying the same body returns the prior result without duplicate
messages/audit events. Changed payload with the same key returns 409. Replies and
status changes require expected_version. Row locks and version checks prevent
lost updates; stale callers refresh rather than overwrite another participant.
The UI retains drafts on conflicts, reuses keys after ambiguous failures and
only displays success after server confirmation.

Account activity/token-version/admin role are revalidated before writing.
Persistent throttling permits 30 support writes per account per 15-minute window;
retries count toward this bound. Rate-limit accounting uses the existing separate
transaction, while ticket/message/audit writes commit or roll back together.
Lists apply requester scope, status and literal subject search before bounded
pagination. Messages are ordered oldest-first with page navigation. No automatic
infinite thread download is performed.

All support responses are no-store. Subjects/messages have length limits and
control-character validation, are rendered as escaped plain text in React, and
are never put into audit events or notification templates. No attachments, email
forwarding or external notifications are generated by this phase. Users are warned
not to submit passwords, OTPs, QR tokens or payment credentials. The system cannot
guarantee that arbitrary free text does not contain secrets: support text is private
application data and requires access controls, backup protection and retention
review. No automatic content-redaction or arbitrary deletion policy is invented.

Audit records identify actor, action, ticket ID, timestamp and allowed status
transition; never message/subject text. Coverage reports include SUPPORT only
when the support and operational flags are enabled.
